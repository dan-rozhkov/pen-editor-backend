# Jev-роутинг скиллов в чате

**Дата:** 2026-09-17
**Статус:** shipped (verified live)
**Затрагивает:** `pen-editor-backend` (`src/ai/skillRouting.ts`, `src/ai/chatTurn.ts`, `src/ai/taskPolicy.ts`, `src/services/systemone.ts`, `src/config.ts`)
**История:** заменяет `docs/specs/2026-09-17-jev-triage-design.md` (коммит `c78749a`, откачен `2848e9d`) — см. "Что изменилось со второй попытки" ниже.

## Что такое Jev

Jev ("System One") — модель оценки от TypeSafe AI (`src/services/systemone.ts`):
на вход подаётся произвольный текст/состояние и набор вопросов, на выход —
структурированные ответы. Три типа вопросов:

- **`noul`** — вероятность "да" в 0..1. `criteria` — ОБЪЕКТ с опциональными
  подсказками `{ true?, false? }` для формулировки. Ответ — `{ type: "noul",
  noul: number }`, БЕЗ поля `confidence` — вендор никогда его не присылает для
  этого типа вопроса.
- **`choice`** — выбор одного варианта из перечисленных. `criteria` — ОБЪЕКТ
  вида "имя варианта → описание" (`Record<string, string | null>`, `null`
  описание допустим). Ответ — `{ type: "choice", choice, probabilities,
  confidence }`.
- **`score`** — уровень по шкале. `criteria` — УПОРЯДОЧЕННЫЙ МАССИВ описаний
  уровней от низкого к высокому (минимум 2). Ответ — `{ type: "score", score,
  legend, probabilities, confidence }`.

Ключевая деталь, на которой споткнулась первая реализация: поле промпта
называется **`instructions`**, не `question`. Ответы `choice` и `score`
обязательно несут `confidence`, `noul` — никогда. `model` в теле запроса
**обязателен** — без него вендор отвечает 422.

Вендор оценивает вопросы одного запроса параллельно ("speculative fan-out"),
поэтому несколько вопросов в одном `evaluate()`-вызове стоят немногим больше
одного — это не используется текущим единственным потребителем (он задаёт
ровно один вопрос), но объясняет форму API (`questions: Record<string, Q>`,
`answers` с теми же ключами).

## Единственный потребитель: роутинг скиллов в чате

Сегодня, если пользователь пишет что-то вроде "сделай кликабельный прототип
логина" без явного `/prototype`, модель сама вынуждена: прочитать каталог
"Available Skills" в системном промпте, вызвать `load_skill`, дождаться
результата — и только потом продолжить настоящую работу. Это целый лишний ход
модели ради одного решения "какой скилл тут просится". `routeSkill()`
(`src/ai/skillRouting.ts`) задаёт Jev один `choice`-вопрос с вариантами —
имена куратируемых скиллов (только `getAllSkills()`, без пользовательских и
learned — они решаются отдельно, см. ниже) плюс `none` — и `prepareChatTurn`
(`src/ai/chatTurn.ts`) вставляет ответ ДО первого хода модели, синтетической
парой `lookup_skill` с пустым `input: {}`, той же техникой, что и явный
`/skill`.

Другого потребителя `systemone.ts` в этой кодовой базе нет. Первая попытка
(см. историю ниже) заводила ещё и офлайн-триаж перед `extractInsights` в
`src/analysis/triage.ts` — этот путь **не восстановлен**: `TRIAGE_MODE`,
`TRIAGE_THRESHOLD` и сам `triage.ts` не существуют в этой версии. `systemone.ts`
написан достаточно общо (типизированный `evaluate<Q>`), чтобы второй
потребитель мог появиться позже без переделки клиента, но это осознанно
отдельное решение на будущее, а не часть текущей фичи.

## Что изменилось со второй попытки

Первая версия (`c78749a`) говорила с Jev через Vercel AI Gateway, как со
всеми остальными моделями в этом проекте (единый путь провайдера). Она была
откачена, потому что это не сработало: **Jev обслуживается ровно одним
провайдером — самим TypeSafe** — его нет в каталоге OpenRouter, а Vercel AI
Gateway на бесплатных кредитах отвечает `403 RestrictedModelsError` на эту
модель — это тарифная политика, а не сбой, и BYOK, по жалобам в комьюнити,
упирается в то же ограничение. Тогда весь код, тесты и ревью были готовы
раньше, чем выяснилось, что вызвать модель нечем; отсюда правило, по которому
сделана вторая попытка: доступность модели проверяется ЖИВЫМ вызовом до того,
как написана хоть строчка интеграции.

Фикс — говорить с нативным REST API TypeSafe напрямую:

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <TYPESAFE_API_KEY>
Content-Type: application/json

{ "model": "...", "state": "...", "questions": { ... } }
```

Никакого SDK, никакого Gateway — `src/services/systemone.ts` использует
глобальный `fetch` напрямую, тем же паттерном, что `src/analysis/embeddings.ts`
(`createEmbedder`): фабрика, которая возвращает `null`, если ключ не выставлен,
и принимает инъекцию `fetchFn` для тестируемости. Ретраи (429/529, до 3 попыток,
экспоненциальный бэкофф, потолок на `Retry-After` — `MAX_RETRY_AFTER_MS =
10_000`, чтобы не проспать чат-бюджет `SKILL_ROUTING_TIMEOUT_MS = 1_500` на
одном вендорском ответе) и таймаут (`REQUEST_TIMEOUT_MS = 30_000` как потолок
на весь вызов включая ретраи) реализованы в клиенте, а не полагаются на
поведение SDK, которого больше нет.

## Верификация вживую (2026-09-17)

Перед тем как полагаться на маршрутизацию, интеграция была прогнана против
настоящего API TypeSafe (не мока):

| Проверка | Результат |
|---|---|
| `GET /v1/models` | отдаёт `jev-latest` и `jev-preview` |
| Запрос модели `jev-latest` | реально отвечает `jev-1.13.0` |
| Пробный набор из 15 сообщений против настоящего куратируемого каталога (35 скиллов) | 15/15 верных маршрутов — единственный кажущийся промах, `critique` на "review this design and tell me what's wrong", оказался верным пиком против НЕВЕРНОГО ожидания в самом пробном наборе |
| Задержка на вызов | 260–720 мс, типично ~280 мс — против бюджета `SKILL_ROUTING_TIMEOUT_MS = 1500` мс |
| Уверенность на явных пиках | 0.87–1.00 |
| "make the button 4px bigger" | confidence 0.60 — корректно упало ниже порога `SKILL_ROUTING_MIN_CONFIDENCE = 0.7` |
| "привет", "what fonts am I using here?" | вернули явный вариант `none` |
| Токены на пробный запрос (3 вопроса, короткий state) | 482 input tokens |
| Токены на НАСТОЯЩИЙ роутинг-вызов (35 скиллов + `none` в `criteria`) | 1782 input tokens |
| Прайсинг | $0.042 / 1M input tokens, output — бесплатно |
| Стоимость роутинга | $0.000075 за ход ≈ **$7.48 на 100 000 чат-ходов** — против целого лишнего хода дорогой модели, который он убирает |

Живой смоук подтверждает не только "клиент умеет достучаться до вендора", но
и два продуктовых допущения сразу: порог 0.7 реально отсекает
неоднозначные правки, а не только теоретически, и задержка вендора
укладывается в чат-бюджет с большим запасом (280 мс из 1500 мс), а не впритык.

## Три режима, дефолт — `off`

`SKILL_ROUTING_MODE` (`src/config.ts`): `off` (дефолт) / `shadow` / `enforce`.

- **off** — Jev не вызывается вообще.
- **shadow** — Jev вызывается, вердикт логируется, но НИЧЕГО не внедряется в
  ход. Вызов **не блокирует** ход: `prepareChatTurn` не делает на него
  `await`, а вешает `.then()`/`.catch()` и продолжает собирать запрос к
  модели — см. "TTFT-бюджет" ниже.
- **enforce** — уверенный пик (`confidence >= SKILL_ROUTING_MIN_CONFIDENCE`,
  дефолт 0.7) реально внедряется: `skillContent` берётся из найденного
  скилла, и `slashSkillName` выставляется в имя пика — почему это
  обязательно, см. "Связка с FIR-45" ниже.

Дефолт — `off`, не `shadow`. Это единственный потребитель `TYPESAFE_API_KEY`
в проекте (второй, офлайн-триажный, не существует в этой версии), но принцип
из первой попытки остался верным и стал проще: этот путь живёт прямо в
`/api/chat`, а не в офлайн-CLI. Если бы дефолтом был `shadow`, выставление
`TYPESAFE_API_KEY` само по себе тихо добавило бы сетевой вызов Jev к каждому
чат-ходу пользователя. Установка ключа не должна сама по себе включать
пользовательский сетевой вызов; `SKILL_ROUTING_MODE` включается явно, отдельно
от факта наличия ключа, деплой за деплоем.

## TTFT-бюджет и почему shadow не блокирует

`SKILL_ROUTING_TIMEOUT_MS = 1_500` — осознанный бюджет just for this call,
малый по сравнению с многосекундным ходом LLM, но достаточный, чтобы дать Jev
реальное окно на ответ (живой прогон показал ~280 мс типично — бюджет щедрый,
не впритык). В `enforce`-режиме этот `await` — единственная легитимная цена:
без ответа Jev нечего внедрять. Но `shadow` по определению ничего не меняет в
ходе — если бы он всё равно делал `await routeSkill(...)`, то чисто
измерительный режим добавлял бы до 1.5с к time-to-first-token каждого
чат-запроса, то есть "измерить перед тем как доверять enforce" стоило бы
пользователю реальной задержки. Поэтому в shadow вызов делается БЕЗ `await`
("fire-and-forget"), лог пика пишется в `.then()` уже после того, как ход ушёл
дальше, а `.catch()` навешан отдельно — `routeSkill` и так fail-open и никогда
не должен бросать, но необработанный `reject` от изменившейся в будущем
реализации не должен превращаться в unhandled rejection процесса. Лог пика
пишется БЕЗУСЛОВНО, а не под `ENABLE_AGENT_LOGGING` (выключен по умолчанию) —
иначе "измерить перед тем как доверять" неизмеримо по умолчанию. Пик, чьё имя
не резолвится через `getSkill` (устарел, переименован), тоже логируется, а не
отбрасывается молча.

## Fail-open — единственный жёсткий инвариант

`routeSkill` перехватывает любую ошибку клиента (rate limit, таймаут, сетевой
сбой, невалидный ответ, неожиданный тип ответа на `choice`-вопрос) и
возвращает `{ skill: null, confidence: 0, reason: "error" }`. Сломанный или
зарейтлимиченный Jev не должен никогда сломать или заблокировать чат-ход —
модель просто вызывает `load_skill` сама, ровно как сегодня без этой фичи.
Это единственный инвариант, который переживает в любом режиме, включая
`enforce`.

## Тул-петля: один ход — несколько HTTP-запросов

Тулы исполняются в браузере, поэтому один ход пользователя приходит на бэкенд
несколькими запросами: первый заканчивается сообщением пользователя, каждое
продолжение — ассистентским. Исходно `prepareChatTurn` смотрел только на
`messages[messages.length - 1]`, и это давало тихий баг, который Jev просто
сделал заметнее (он существовал и для явных `/slash`): начиная со второго шага
скилл не резолвился вообще. Синтетическая пара живёт только в серверном
массиве и никогда не уходит клиенту, так что история клиента её не несёт —
значит, модель переставала видеть инструкции, которым всё ещё должна была
следовать, а `resolveTaskPolicy` откатывался в `"native"` посреди прототипа и
выдавал нативный `batch_design` вместо embed-only.

Чинится тем, что и слэш-команда, и Jev-роутинг, и точка вставки синтетической
пары считаются от **последнего ПОЛЬЗОВАТЕЛЬСКОГО сообщения** (`lastUserIndex`),
а не от последнего вообще. Побочный и важный эффект: префикс сообщений теперь
одинаков на всех шагах одного хода — до фикса пара исчезала на втором шаге и
ломала prompt-кэш ровно там.

Два следствия, которые пришлось закрыть отдельно:

- **Счётчик использования пользовательских скиллов** (`bumpUse`) теперь под
  `isFreshUserTurn`. Иначе ход из десяти шагов накручивал бы десять
  использований одной слэш-команде.
- **Вердикт Jev мемоизируется** по `(текст, список кандидатов, порог)` на 10
  минут (`ROUTE_CACHE_TTL_MS`, максимум 500 записей). Без этого enforce платил
  бы латентностью и токенами за каждый шаг петли вместо одного раза за ход —
  ~280 мс к TTFT каждого шага за ответ, который не может измениться, потому
  что вход вопроса побайтово тот же. Вердикт `reason: "error"` НЕ кэшируется:
  это факт про транспорт, а не ответ про сообщение, и пинить одну сетевую
  икоту на десять минут — худшее, что можно сделать.

## Границы того, что уходит вендору

- Текст обрезается до `MAX_ROUTED_TEXT_CHARS = 2000` **до** `scrubPii`, не
  после: роутеру нужна форма запроса, а не содержимое, а вставленный
  100-килобайтный HTML иначе улетал бы вендору на каждом ходу и в enforce
  сжирал бы весь TTFT-бюджет. Порядок важен — обрезать уже очищенную строку
  значит рискнуть разрезать редакцию пополам.
- Скилл с именем `none` исключается из кандидатов с предупреждением в лог.
  Скиллы — просто markdown-файлы без защиты имени, а совпадение с
  sentinel-вариантом сделало бы `choice === "none"` двусмысленным: скилл стал
  бы навсегда нероутируемым, а любое неоднозначное сообщение читалось бы как
  осознанный отказ.

## Аналитика: `skill_source`

`agent_turn_completed` теперь несёт `skill_source: "slash" | "auto" | null`
рядом с `skill`. Enforce-пик выставляет тот же `slashSkillName`, что и
настоящая слэш-команда (этого требует FIR-45, см. ниже), поэтому без
отдельного поля «пользователь попросил скилл» и «Jev угадал скилл» слились бы
в одно значение — ровно та разница, на которой строится вывод о том, стоит ли
держать `enforce` включённым.

## Связка с FIR-45 и `slashSkillName`

`resolveTaskPolicy` (`src/ai/taskPolicy.ts`) — структурный guard из FIR-45,
который подменяет `batch_design` на embed-only вариант в режиме
prototype/slides. Он доверяет только двум сигналам: явному `/slash` на
текущем сообщении (`slashSkillName`) или `load_skill`-вызову с именем
`"prototype"`/`"slides"` где-то в истории. Синтетическая пара, которую
`prepareChatTurn` вставляет для Jev-пика, использует имя инструмента
`lookup_skill` с пустым `input: {}` — она не матчится ни под один из этих двух
сигналов. Поэтому `enforce`-пик обязан явно выставить `slashSkillName =
verdict.skill` — иначе модель получает системный промпт с "Agent Mode:
prototype" (из содержимого скилла), а `taskPolicy` остаётся `"native"`, и
модель получает нативный `batch_design` вместо embed-only варианта, то есть
может создавать настоящие сцен-ноды там, где ожидается только HTML-эмбед.
`shadow`-режим этот `slashSkillName` не трогает — он ничего не внедряет, ход
остаётся ровно таким, каким был бы без Jev.

## Кандидаты — только куратируемые скиллы

`routeSkill`'s `candidates` собираются из `getAllSkills()` — сознательно не
расширены на пользовательские (`user_skills`) или learned (`agent_skills`)
скиллы. Обе эти категории требуют собственных Postgres-чтений (уже есть в
`prepareChatTurn`, за собственными таймаутами), и их включение в Jev-пик —
отдельное решение на будущее, а не побочный эффект этой фичи. Если пользователь
явно вызывает `/my-skill` слэш-командой, обычный путь резолва в
`prepareChatTurn` срабатывает раньше, и Jev вообще не спрашивается.

## Что происходит с текстом, когда `/slash` не резолвится

Если сообщение начинается с "/что-то", но это "что-то" не куратируемый и не
пользовательский скилл (вставленный путь вроде `/Users/me/shot.png ...`,
опечатка, "/как дела"), Jev всё равно роутится на текст БЕЗ слэш-токена — само
наличие "/" в начале не несёт смысла, который стоит показывать модели оценки.
Отдельный случай: если слэш-команда называет реальный, но выключенный
пользователем скилл (`/mysk`, где `mysk` существует, но `enabled: false`) —
авто-пик не выполняется вообще, ни на каком тексте: этот скилл намеренно
нерезолвируем (как и в `load_skill`), и позволить Jev'у подсунуть другой
куратируемый скилл для того же сообщения было бы обходом этого осознанного
решения пользователя.

## PII

`routeSkill` пропускает текст сообщения через `scrubPii` (`src/analysis/pii.ts`)
перед отправкой — Jev сторонний вендор, получающий пользовательский текст, и
это та же осторожность, что и у офлайн-аналитического пайплайна.

## Аддендум (2026-09-20): двухпроходный роутинг вместо одного `choice` + `none`

**Статус:** shipped. Переписывает `src/ai/skillRouting.ts` и Jev-блок в
`src/ai/chatTurn.ts` целиком; портирует дизайн из собственного кукбука
TypeSafe для этой же задачи —
[docs.typesafe.ai/cookbooks/skill_suggestion](https://docs.typesafe.ai/cookbooks/skill_suggestion),
который на ростере Hermes (182 скилла, 488 запросов) измерил снижение доли
неверных загрузок скилла больше чем вдвое (16.8% → 7.3%) и почти втрое для
загрузок "в никуда" (9.8% → 4.0%) относительно baseline-агента с одним
списком скиллов.

### Почему старый дизайн (один `choice` + sentinel `none`) был неверным примитивом

Старая версия задавала Jev'у ОДИН вопрос типа `choice` над всеми куратируемыми
скиллами плюс синтетический вариант `"none"` ("сообщение ни под что не
подходит"). Это смешивает две разные вещи в одном вопросе:

- **"Какой скилл лучше остальных?"** — вопрос ОТНОСИТЕЛЬНЫЙ: он всегда
  выбирает лучшего из перечисленных вариантов, даже если ВСЕ они плохие.
- **"Нужен ли вообще какой-то скилл?"** — вопрос АБСОЛЮТНЫЙ: да/нет само по
  себе, не относительно других вариантов.

`choice` (`Choice` в терминах Jev) отвечает только на первый вопрос. Засовывая
`"none"` внутрь него как ещё один вариант, мы заставляли модель взвешивать
"это не подходит ни под что" на той же относительной шкале, что и "это скилл
X, а не скилл Y" — ровно та путаница, о которой предупреждает
[docs.typesafe.ai/model-jaggedness/jev-1.13.md](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)
в разделе "Common-sense structural invariants": вероятность `noul`-вопроса и
`probabilities["да"]` эквивалентного `choice`-вопроса на одном и том же
сообщении НЕ обязаны совпадать, и порог, откалиброванный на одном примитиве,
не переносится на другой без потерь.

### Новый дизайн: два прохода, `choice` для "какой" и `noul` для "нужен ли вообще"

**Проход 1** (`runPass1`, один вызов `evaluate()`):

- `choice` `which` над ВСЕМИ куратируемыми скиллами (без sentinel `none` —
  весь блок-коллизия из старой версии удалён вместе с ним).
- Три вопроса `noul` над тем же `state`, отвечающие не на тему сообщения (в
  редакторе дизайна тема всегда "дизайн"), а на его ФОРМУ — процесс по
  инструкции или прямая правка:
  - `documented_workflow` — "Would a careful designer handling this request
    follow a specific named workflow with its own steps and conventions … —
    rather than simply making the requested change directly?"
  - `substantial_new_work` — "Is the user asking for a substantial new piece
    of design work … rather than a small, self-contained tweak to something
    that already exists?"
  - `direct_edit_suffices` (**инвертированный** — да здесь означает "скилл
    НЕ нужен") — "Could a competent designer fully satisfy this request with
    a single direct edit to the canvas … with no special process, handoff,
    or multi-step workflow involved?"

  Инверсия `direct_edit_suffices` обрабатывается явно в коде
  (`INVERTED_GATE_KEYS`, `1 - noul`) ДО усреднения — три "ориентированных"
  значения усредняются в `gate`. Если `gate < SKILL_ROUTING_GATE_THRESHOLD`
  (новый конфиг, default `0.3` — то же число, что и в кукбуке), возвращается
  `{ skill: null, reason: "gated" }`, и проход 2 не выполняется вовсе.

**Проход 2** (`runPass2`, ещё один `evaluate()`, только если прошёл гейт):

- Шорт-лист — топ-3 кандидата прохода 1 по `probabilities` (`SHORTLIST_SIZE`).
- `choice` `which` над этими тремя, но с более богатым `criteria`: полное
  описание скилла + первые `EXCERPT_CHARS` (700, значение из кукбука) символов
  его собственного markdown-тела (`Skill.content` из `skills.ts` — фронтматтер
  там уже отрезан парсером, `stripFrontmatter` в `skillRouting.ts` — защита на
  случай, если это когда-нибудь перестанет быть так).
- Один `noul` `fits::<name>` НА КАЖДОГО кандидата — абсолютный вопрос "делает
  ли именно этот скилл то, что просят конкретно в этом сообщении". Это может
  оказаться низким у всех трёх сразу, даже если `choice` уверенно выбрал
  "лучшего из трёх плохих" — именно то различие, ради которого в проходе 2
  используются ОБА примитива одновременно, а не только `choice`.

Если `fits[победитель choice'а]` ниже `SKILL_ROUTING_FITS_THRESHOLD` (новый
конфиг, default `0.3`) — `{ skill: null, reason: "no-fit" }`. **Важно: гейт
читает fit САМОГО победителя, а не максимум по всему шортлисту** — это две
разные величины, если Choice-победитель прохода 2 не совпадает с кандидатом,
у которого самый высокий персональный `fits::<name>`. Гейт на максимуме по
шортлисту — баг, живший здесь до 2026-09-20: он мог внедрить кандидата с
собственным fit 0.05, потому что КАКОЙ-ТО ДРУГОЙ кандидат в шортлисте набрал
0.92 — ровно тот ложноположительный результат, ради предотвращения которого
проход 2 существует. Отсутствие записи для победителя в `fits` (не должно
происходить, `fits` строится по тому же шортлисту, по которому шёл `choice`)
закрывает гейт, а не пропускает. Иначе победитель прохода 2 всё ещё
проверяется на `SKILL_ROUTING_MIN_CONFIDENCE` — ниже него `reason:
"low-confidence"`. `SkillRouteVerdict.winnerFit` репортит именно то значение,
на котором был гейт, отдельно от полного `fits`.

### Бюджет: один общий дедлайн на оба прохода, а не два независимых

`SKILL_ROUTING_TIMEOUT_MS` (1.5с) остался бюджетом ОДНОГО сетевого вызова, но
добавлен `SKILL_ROUTING_ENFORCE_BUDGET_MS` (новый конфиг, default `2500`) —
общий дедлайн на оба вызова `evaluate()` вместе, actual для `enforce`-режима,
который ждёт ответ на пути запроса перед TTFT. Один `AbortSignal.timeout(...)`
создаётся один раз в начале `routeSkill` и участвует (через `AbortSignal.any`)
в сигнале КАЖДОГО из двух вызовов — так что превышение бюджета на прогреве
прохода 1 оставляет проходу 2 меньше времени, а не сбрасывает счётчик.

Если общий бюджет истёк (или проход 2 упал по любой другой причине) уже
ПОСЛЕ того, как проход 1 успешно ответил — `routeSkill` не выбрасывает всё
целиком, но и **не** внедряет победителя прохода 1 (см. "Ревизия 2026-09-20,
раунд 2" ниже: более ранняя версия этого документа здесь ошибочно описывала
откат как `reason: "picked"`/`"low-confidence"` с внедрением — это было
исправлено). Вместо этого — отдельный `reason: "budget"`, `skill: null`
всегда, а победитель/уверенность прохода 1 репортятся в отдельных полях
`pass1Winner`/`pass1Confidence` только для измерения в shadow-режиме.

`shadow`-режим никогда не await'ится в `chatTurn.ts`, поэтому не обязан быть
быстрым — он использует отдельную, гораздо более щедрую константу
`SKILL_ROUTING_SHADOW_BUDGET_MS` (8с, не конфиг — намеренно зашито в код,
потому что таймингом shadow-режима не должно управлять ничего кроме "не течь
бесконечно").

### `SkillRouteVerdict`: теперь пригоден для анализа, а не только для решения

Раньше `logPick` в `chatTurn.ts` рано выходил на `!verdict.skill` — значит,
`shadow`-режим логировал только те ходы, где он БЫ сработал, и по логам было
невозможно оценить долю ложноотрицательных срабатываний. Теперь `chatTurn.ts`
логирует КАЖДЫЙ вердикт, в обоих режимах, одной строкой:
`[skillRouting] <JSON.stringify(verdict + mode [+ resolves])>`. `SkillRouteVerdict`
расширен: `reason` (`"picked" | "gated" | "no-fit" | "low-confidence" |
"unavailable" | "budget" | "error"`), `gate` + `gateValues` (уже
ориентированные), `top3` (имя+вероятность из прохода 1), `fits` (когда проход
2 выполнялся), `model`, `pass1Ms`/`pass2Ms`, `inputTokens`/`outputTokens`,
`pass1Winner`/`pass1Confidence` (только при `reason: "budget"` — см. "Ревизия
2026-09-20, раунд 2" ниже). Ни текста сообщения, ни какого-либо содержимого
`state` в вердикте нет и в лог не попадает — только коды причин и числа.
`resolves: false` добавляется в залогированную запись отдельно, когда
`verdict.skill` не резолвится через `getSkill()` — раньше это тоже терялось
(ранний `return` до всякого лога).

### Контекст: `recent_context` в `state`

`state`, отправляемое в Jev, теперь объект `{ request, recent_context }`
(вместо голой строки). `recent_context` — короткий хвост переписки ДО текущего
хода (`buildRecentContext` в `chatTurn.ts`: до 4 последних user/assistant
сообщений, только текстовые части, без тул-коллов/результатов, по 500 симв.
на сообщение, собранные в порядке oldest→newest). Обрезка до
`MAX_CONTEXT_CHARS` и `scrubPii` — уже ВНУТРИ `routeSkill`, ПОСЛЕ построения
строки в `chatTurn.ts` — тот же порядок "обрезать, потом скрабить", что и у
`messageText`/`MAX_ROUTED_TEXT_CHARS`, по той же причине (обрезка скрабленной
строки может разрезать редакцию пополам). **Обрезка берёт ХВОСТ строки, не
начало** (`truncateTail`, не `slice(0, …)`) — это единственная часть, которую
можно резать без потери смысла: `buildRecentContext` уже собирает саму
БЛИЖАЙШУЮ к текущему ходу четвёрку сообщений в правильном порядке, но их
суммарная длина может превышать `MAX_CONTEXT_CHARS`; резать с начала (баг,
живший здесь до 2026-09-20) выбрасывало именно то сообщение, которое стоит
непосредственно перед текущим — единственное, способное разрешить "теперь
сделай то же самое для экрана логина". Кандидаты по-прежнему только
куратируемые скиллы — раздел "Кандидаты — только куратируемые скиллы" выше не
изменился.

### Кэш вердиктов

Ключ кэша расширен: помимо текста и порогов теперь включает `recentContext`
(тот же хвост, что и выше) и оба новых порога (`gateThreshold`,
`fitsThreshold`) — любое изменение любого из них означает промах кэша, а не
устаревшее попадание. `error`-вердикт по-прежнему никогда не кэшируется.
Правило для `reason: "budget"` изменилось во втором раунде ревью — см.
"Ревизия 2026-09-20, раунд 2" ниже: она ТЕПЕРЬ кэшируется, но на отдельной,
короткой TTL (`ROUTE_CACHE_SHORT_TTL_MS`, ~60с), а не совсем без кэша, как
было в первом раунде.

## Ревизия 2026-09-20, раунд 2

Второй раунд ревью этого дизайна нашёл, что раунд 1 сам внёс регрессию и
пропустил один пограничный случай. Правки:

1. **Откат прохода 1 без прохода 2 бывший здесь описан как внедряющий
   победителя (`reason: "picked"`/`"low-confidence"`) — это и был баг.**
   Раунд 1 сделал этот откат НЕкэшируемым именно для того, чтобы шаг 2 того
   же тул-луп-хода мог заново попытать проход 2 — но параллельно с этим он
   продолжал ВНЕДРЯТЬ победителя прохода 1 без проверки `fits`, то есть
   ровно то, ради недопущения чего проход 2 вообще существует. Хуже того:
   проход 1 больше не предлагает `choice`-вариант "никакой скилл не
   подходит" (см. выше) — значит проход 1 ОБЯЗАН назвать какого-то
   победителя на КАЖДОМ сообщении, и именно откат-без-прохода-2 был
   единственным путём, который внедрял этот принудительный выбор без
   `fits`-проверки. Исправлено: такой откат теперь ВСЕГДА резолвится в
   `{ skill: null, reason: "budget" }` — победитель и уверенность прохода 1
   репортятся отдельными полями `pass1Winner`/`pass1Confidence` только для
   измерения в shadow-режиме, но никогда не становятся `verdict.skill`.
2. **Кэш этого отката меняется на короткую TTL, а не "не кэшировать
   вовсе".** Шаги одного тул-луп-хода должны сходиться к одному и тому же
   решению (иначе шаг 1 внедряет скилл/`slashSkillName`/FIR-45-политику, а
   шаг 2 — при заново успешном проходе 2 — говорит "no-fit", и всё это
   пропадает посреди хода). Полное отсутствие кэша здесь возвращало именно
   этот баг. Новая константа `ROUTE_CACHE_SHORT_TTL_MS` (~60с, рядом с
   `ROUTE_CACHE_TTL_MS` в коде) — компромисс: достаточно долго для
   реалистичного многошагового хода, значительно короче обычных 10 минут,
   чтобы один транспортный сбой не подавлял роутинг на СЛЕДУЮЩИХ,
   несвязанных ходах с тем же ключом кэша.
3. **У прохода 1 не было проверки на пустой `probabilities`.**
   `browseStep.ts` в этом же диффе завёл `hasProbabilities()` для той же
   вендорской особенности (иначе валидный по форме choice-ответ может
   нести `probabilities: {}`). У прохода 1 такой проверки не было: пустой
   `probabilities` → пустой `ranked` → пустой шорт-лист →
   `pass1Budget`-откат, ЗАКЭШИРОВАННЫЙ, при том что проход 2 не запускался
   вовсе. Исправлено: пустое/отсутствующее распределение в choice-ответе
   прохода 1 теперь `throw` внутри `runPass1`, что resolves в `reason:
   "error"`, БЕЗ кэша — как и любой другой малформед-ответ прохода 1.
4. **Шорт-лист прохода 2 строился только по топ-3 `probabilities`, а не по
   `which.choice`.** `choice` и `probabilities` — отдельные поля ответа;
   ничто не гарантирует, что `choice` — это argmax `probabilities`.
   Исправлено: `pass1.winner` теперь ВСЕГДА объединяется в шорт-лист
   (`Set`, не просто `top3`), так что кандидат, которого проход 1 реально
   выбрал, всегда получает свой `fits`-нуль в проходе 2, даже если его
   личная вероятность оказалась ниже топ-3.
5. **`stripFrontmatter` — вторая, ненужная зачистка уже зачищенного
   тела.** `Skill.content` из `skills.ts` уже без фронтматтера — тот же
   регекс, применённый повторно, не защита, а риск: скилл, чьё тело
   легитимно открывается тематическим разделителем `---` с ещё одним `---`
   ниже, потерял бы всё до второго `---` как "фронтматтер". Хелпер и оба
   вызова удалены; `cacheKey`/`runPass2` используют `candidate.content`
   напрямую.
6. **`CHOICE_INSTRUCTIONS` всё ещё спрашивал "which of these skills, IF
   ANY"**, хотя вариант "никакой" убран из Choice ещё в первой ревизии этого
   дизайна (см. выше). Переформулировано на "which... is the closest fit" —
   вопрос "нужен ли скилл вообще" целиком остаётся за тремя gate-нулями,
   не за этим Choice.

## Ревизия 2026-09-20, раунд 3

Третий раунд ревью (общий для `skillRouting.ts` и `browseStep.ts`) нашёл, что
раунд 2 сам оставил один непокрытый бюджетный путь и один устаревший гейт.
Правки, актуальные для этого файла:

1. **`SKILL_ROUTING_SHADOW_BUDGET_MS` (8с) был мёртвой константой.**
   `perCallSignal()` жёстко ограничивал КАЖДЫЙ вызов `evaluate()`
   `SKILL_ROUTING_TIMEOUT_MS` (1.5с) — независимо от режима — так что два
   прохода shadow-режима физически не могли превысить ~3с, и заявленный 8с
   потолок никогда не мог сработать. Хуже: это цензурировало именно те
   данные, ради которых существует shadow-режим — Jev, честно ответивший на
   проход 1 за 2с под нагрузкой, читался как `reason: "error"` (таймаут
   1.5с) вместо реального вердикта. Исправлено: добавлен
   `RouteSkillOptions.perCallTimeoutMs` — per-call потолок, отдельный от
   `overallBudgetMs`. `enforce`-режим по-прежнему получает жёсткий
   `SKILL_ROUTING_TIMEOUT_MS` (это TTFT-бюджет одного сетевого вызова);
   `chatTurn.ts`'s shadow-вызов теперь передаёт `SKILL_ROUTING_SHADOW_BUDGET_MS`
   и как `overallBudgetMs`, и как `perCallTimeoutMs` — каждый вызов
   ограничен тем, что осталось от общего бюджета (через `AbortSignal.any`),
   а не отдельным жёстким числом, унаследованным от TTFT-пути, на который
   shadow-режим никогда не попадает.
2. **`SKILL_ROUTING_MIN_CONFIDENCE` = 0.7 незаметно ужесточился, когда гейт
   переехал с прохода 1 (весь каталог, десятки кандидатов) на победителя
   прохода 2 (шорт-лист из 3-4).** `confidence` — детерминированная функция
   от пика И числа опций (`(n*peak-1)/(n-1)`): при 0.7 и n=36 (типичный
   каталог прохода 1) это соответствует пику ≈0.71, а при n=3-4 (шорт-лист
   прохода 2) то же 0.7 требует пика ≈0.80 — ровно тот же артефакт числа
   опций, ради ухода от которого `browseStep.ts` в этом же диффе переехал на
   пиковую вероятность. Исправлено: гейт победителя прохода 2 теперь читает
   ПИКОВУЮ ВЕРОЯТНОСТЬ победителя (`peakProbability`, зеркало одноимённого
   хелпера в `browseStep.ts`, не экспортированного оттуда — продублирован, а
   не импортирован), а не вендорский `confidence`. Тот же конфиг-var
   (`SKILL_ROUTING_MIN_CONFIDENCE`), но дефолт понижен до `0.6` — значение
   `0.7` было откалибровано под гейт на полном каталоге прохода 1 и не
   переносится на маленький шорт-лист. `confidence` по-прежнему репортится в
   вердикте (`SkillRouteVerdict.confidence`), рядом с новым полем
   `SkillRouteVerdict.peak`, так что shadow-логи несут оба числа. Проход 2
   заодно получил ту же защиту от пустого `probabilities`, что и проход 1
   (`hasProbabilities`) — иначе пустое распределение читалось бы как пик 0 и
   ложно проваливало бы гейт.
3. **Документация `SKILL_ROUTING_FITS_THRESHOLD` противоречила коду.**
   И `config.ts`, и `.env.example` утверждали "лучший из трёх кандидатов
   шорт-листа должен пройти порог, иначе весь шорт-лист отбрасывается" — но
   код (см. "Ревизия... раунд 1", finding #1 выше) гейтит на fit САМОГО
   ПОБЕДИТЕЛЯ, а не на максимум по шорт-листу. Документация исправлена в
   обоих местах, чтобы описывать код как есть.
4. **`cacheKey` сериализовал тело КАЖДОГО кандидата на КАЖДЫЙ запрос.**
   Ключ включал `content.slice(0, EXCERPT_CHARS)` для всех кандидатов —
   ~30 КБ `JSON.stringify` на каждый чат-запрос, включая каждый шаг
   тул-петли, и до ~15 МБ удержанных данных на `ROUTE_CACHE_MAX_ENTRIES`
   (500) ключей. Куратируемый каталог грузится один раз при старте и
   идентичен между запросами, так что тела кандидатов не добавляют ключу
   различимости. Исправлено: `cacheKey` теперь несёт только
   `[name, description]` по каждому кандидату плюс дешёвый "отпечаток"
   каталога (`catalogFingerprint` — количество кандидатов + суммарная длина
   их `content`, оба O(1)/O(n) без сериализации), который всё равно
   меняется, если каталог меняется.

Не относится к `skillRouting.ts`, но тот же раунд ревью также поправил
`browseStep.ts` (см. `docs/superpowers/specs/2026-09-18-browse-task-jev-loop-design.md`):
цифровой дайджест элементов вернул флаги `isPassword`/`hasValue` (были
потеряны при переходе на компактный per-element digest), а `goal_met` теперь
требует более строгий порог 0.8, а не 0.65, на ПЕРВОМ шаге задачи (пустая
`history`) — обе правки не задевают этот файл, но обсуждались в одном
ревью.
