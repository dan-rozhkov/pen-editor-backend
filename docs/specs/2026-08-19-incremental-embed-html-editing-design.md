# Точечное редактирование HTML-прототипа агентом

**Дата:** 2026-08-19
**Статус:** design
**Затрагивает:** `pen-editor-backend` (схемы инструментов, промпт), `pen-editor` (хендлеры)

## Проблема

Экран прототипа — это один `embed`-узел, весь HTML которого лежит строкой в
`EmbedNode.htmlContent` (`pen-editor/src/types/scene.ts:933`). Сегодня у агента
нет способа поправить кусок этого HTML: единственный путь — `batch_design` с
`U(id, {htmlContent: "…весь документ заново…"})`.

Отсюда три издержки, и только первая — про деньги:

1. **Стоимость.** Правка одной кнопки = чтение всего экрана (`batch_get` →
   `serializeUtils.ts:148` отдаёт `htmlContent` целиком) плюс выписывание всего
   экрана заново. Типовой экран — 5–10k токенов, то есть ~16k токенов за смену
   цвета.
2. **Риск порчи.** Длинный выход идёт через самописный DSL `batch_design`
   (`pen-editor/src/lib/tools/batchDesign/parser.ts`), где уже пришлось лечить
   обрыв генерации на незакрытой кавычке. Чем длиннее строка `htmlContent`, тем
   выше шанс словить обрыв — и получить пустой белый экран вместо правки.
3. **Дрейф.** Переписывая экран целиком, модель незаметно меняет то, что её не
   просили: отступы, тексты, порядок блоков. Пользователь просил поменять
   кнопку, а поехала вёрстка.

## Решение

Два новых инструмента, разделяющих чтение и правку:

- `read_embed_html` — читает **часть** HTML экрана (структуру или совпадения),
  а не весь документ.
- `edit_embed_html` — применяет список anchor-based правок вида
  `oldString → newString`, ровно как `Edit` в агентных харнессах.

Оба — клиент-исполняемые: схема на бэкенде, исполнение во фронтенде против
живого Zustand-стора (стандартная split-execution архитектура проекта).

Аргументы передаются **обычным JSON tool-call**, а не через DSL `batch_design`.
Экранирование кавычек берёт на себя провайдер, поэтому класс багов с обрывом на
кавычке для правок просто не возникает.

### Почему anchor-based, а не DOM-адресация

Рассматривались три формата адресации правки:

| Формат | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **A. Anchor-based** (`oldString`→`newString`) | Модель знает формат нативно; одинаково адресует разметку и правила внутри `<style>`; работает на любом существующем экране; проверка уникальности даёт честную ошибку | Чувствительность к пробелам; нужен предварительный read | **выбран** |
| B. DOM-адресация (`data-pen-el` / CSS-селектор + set_text/set_attr/replace) | Устойчивее к форматированию; семантично | CSS внутри `<style>` через DOM не адресуется — нужен второй язык операций; штампы id отсутствуют на уже созданных экранах; модель натренирована хуже | отклонён |
| C. Именованные секции (`<!-- #header -->`) | Дёшево на выход | Требует дисциплины генерации; не работает на существующих экранах; не ложится на сквозные правки | отклонён |

Решающий аргумент против B — покрытие: половина дизайнерских правок живёт в
`<style>`, куда DOM-операции не дотягиваются, и пришлось бы держать два
несовместимых языка правок в одном инструменте.

## Контракт: `edit_embed_html`

### Схема (бэкенд, `src/ai/tools.ts`)

```ts
edit_embed_html: tool({
  description:
    "Apply targeted text edits to an existing embed node's HTML instead of rewriting the whole screen. " +
    "Each edit replaces an exact substring (`oldString`) with `newString`. Use this — never batch_design " +
    "`U(id, {htmlContent})` — whenever you are changing part of a screen that already exists. " +
    "Read the relevant fragment with read_embed_html first so your anchors are exact.",
  inputSchema: z.object({
    nodeId: z.string().describe("Id of the embed node to edit."),
    edits: z.array(z.object({
      oldString: z.string().min(1)
        .describe("Exact substring to find. Must occur exactly once unless replaceAll is true."),
      newString: z.string()
        .describe("Replacement text. Empty string deletes the matched fragment."),
      replaceAll: z.boolean().optional()
        .describe("Replace every occurrence instead of requiring a unique match."),
    })).min(1).max(20).describe("Edits applied in order, each against the result of the previous."),
  }),
})
```

### Семантика (фронтенд, `src/lib/tools/editEmbedHtml.ts`)

**Цель правки.** Если у узла есть `sourceTemplate`, правится он, а не
`htmlContent`. `sourceTemplate` — это авторский текст с тегами
document-компонентов (`<c-…>`), а `htmlContent` — его развёрнутая версия
(`pen-editor/src/utils/embedTemplateUtils.ts:16`). Правка развёрнутого HTML
была бы затёрта при следующем разворачивании. После применения правок результат
прогоняется через `normalizeEmbedHtmlForStorage` с актуальной `componentTagMap`
— ровно как это делает `batchDesign/executor.ts:86`.

**Атомарность.** Правки применяются последовательно к строке в памяти. Любая
ошибка (не найдено / не уникально / узел не embed) — стор не трогается вовсе.
Частично применённый набор правок не допускается: частичное исполнение уже
кусало нас в `batch_design` и порождало дубли.

**Уникальность.** `oldString` без `replaceAll` обязан встречаться ровно один
раз. Иначе — ошибка с числом вхождений и тремя первыми контекстами, чтобы
модель могла удлинить якорь сама, не тратя раунд-трип.

**Совпадение — только точное.** Никакой нормализации пробелов: «умное»
совпадение по нормализованному тексту молча промахивается мимо
соседнего похожего блока. При промахе ошибка отсылает к
`read_embed_html` с `mode: "grep"`.

**Компоненты.** Если правится embed, являющийся document-компонентом, после
коммита вызывается `propagateComponentChanges`, чтобы зависимые экраны
перерисовались (та же ветка, что в `batchDesign/index.ts:78`).

**История.** Один `saveHistory` на весь вызов — одна запись undo, как у
`batch_design` и `rename_layers`.

**Ответ модели** (JSON-строка):

```json
{ "nodeId": "…", "editsApplied": 3, "replacements": 4,
  "htmlLength": 7421, "targetedSourceTemplate": true, "issues": [] }
```

Полный HTML в ответ **не** возвращается — иначе экономия на выходе съедается на
входе следующего хода.

## Контракт: `read_embed_html`

```ts
read_embed_html: tool({
  inputSchema: z.object({
    nodeId: z.string(),
    mode: z.enum(["outline", "grep", "full"]).default("outline"),
    pattern: z.string().optional().describe("Literal substring to search for. Required for mode 'grep'."),
    contextLines: z.number().int().min(0).max(20).default(2),
    maxDepth: z.number().int().min(1).max(12).default(4).describe("Nesting depth for mode 'outline'."),
  }).refine((a) => a.mode !== "grep" || (a.pattern ?? "").length > 0, {
    message: "pattern is required when mode is 'grep'",
  }),
})
```

- **`outline`** (по умолчанию) — усечённый, но синтаксически узнаваемый HTML:
  теги и их атрибуты сохраняются дословно, текстовые узлы обрезаются до 40
  символов, поддеревья глубже `maxDepth` сворачиваются в
  `<!-- 12 nodes omitted -->`. Ключевое свойство: атрибуты видны **дословно**,
  значит их можно сразу использовать как якоря для `edit_embed_html`.
- **`grep`** — вхождения `pattern` с `contextLines` строк вокруг и общим
  числом совпадений.
- **`full`** — весь HTML, как сегодня. Оставлен как escape hatch; в ответ
  добавляется предупреждение, если документ длиннее 20k символов.

Побочная польза: `outline` закрывает давнюю жалобу «агент плохо читает
собственный холст» — сейчас у него нет дешёвого способа посмотреть структуру
экрана, только «всё или ничего».

## Промпт

Без явного гейта модель по привычке пойдёт старой дорогой — это ровно тот
сценарий, который потребовал FIRST-DECISION-гейта при routing'е прототипов.
В `src/ai/system-prompt.ts` (секция про embed-экраны) и в `src/skills/prototype.md`
/ `slides.md` добавляется правило:

> Правя **существующий** экран, всегда используй `read_embed_html` →
> `edit_embed_html`. `batch_design` с `U(id, {htmlContent})` допустим только
> когда экран заменяется целиком (иная концепция, а не доработка).

## Совместимость

- **Гейтинг по режимам.** Инструменты добавляются в общий набор; embed-only
  политика (`src/ai/taskPolicy.ts`) их не ограничивает — они по определению
  работают только с embed-узлами. В research-режиме (Refero-only toolset) они
  не участвуют.
- **Showcase runner.** `src/showcase/runner.ts:225` заглушает *все* инструменты
  без `execute` автоматически, поэтому новые инструменты получат заглушку без
  правок. Отдельного удаления, как для `get_screenshot`, не требуется.
- **MCP-мост.** Хендлеры регистрируются в `toolRegistry.ts` и потому
  автоматически доступны через MCP-сервер редактора.

## Тестирование

**Бэкенд** (`test/tools-contract.test.ts`): оба имени добавляются в оба
захардкоженных списка (строки ~42 и ~82) + zod-тесты схем (min/max на `edits`,
обязательность `pattern` при `mode: "grep"`).

**Фронтенд** (`src/lib/tools/__tests__/editEmbedHtml.test.ts`,
`readEmbedHtml.test.ts`), против реального стора через `seedScene()`:

1. уникальный якорь → замена применена, `htmlContent` изменён;
2. неуникальный якорь → ошибка, **стор не изменён**;
3. якорь не найден → ошибка со ссылкой на grep;
4. `replaceAll: true` → все вхождения, счётчик в ответе;
5. атомарность: вторая правка из двух падает → первая тоже не применена;
6. узел с `sourceTemplate` → правится шаблон, `htmlContent` переразворачивается;
7. правка embed-компонента → зависимые экраны обновлены;
8. узел не embed / не существует → внятная ошибка;
9. undo одной записью возвращает исходный HTML;
10. `outline` не длиннее ~1/5 полного HTML на фикстуре реального экрана и
    сохраняет атрибуты дословно.

**Контракт имён** (`pen-editor/src/lib/__tests__/toolContract.test.ts`)
проверяется автоматически, править не нужно.

E2E не требуется: WebGL не задействован, вся логика — строковая.

## Порядок мержа

1. `pen-editor-backend`: схемы + промпт → `main`.
2. `pen-editor`: хендлеры + регистрация в `toolRegistry.ts` → `main`.

Обратный порядок красит `contract`-джобу на каждый пуш фронтенда до прилёта
бэкенда.

## Что сознательно не входит (YAGNI)

- Оптимистичная блокировка (`expectedVersion`/хеш) — документ редактируется
  одним пользователем в одной вкладке; конфликт правок гипотетичен.
- Нормализация пробелов при поиске якоря — молчаливые промахи дороже
  сэкономленного раунд-трипа.
- Regex в `pattern` — литеральной подстроки хватает, а regex открывает
  катастрофический бэктрекинг на чужом вводе.
- DOM-операции (`set_attr`, `insert_before`) — вернёмся, если якоря окажутся
  хрупкими на практике; формат ответа это допускает без слома контракта.
- Точечная правка опубликованных экранов витрины — отдельная задача, тот же
  формат правок можно будет переиспользовать в `showcase:replace-html`.

## Риски

- **Модель промахивается якорем.** Смягчается тем, что `outline` отдаёт
  атрибуты дословно, и внятными ошибками с контекстом. Метрика провала: доля
  вызовов `edit_embed_html`, вернувших ошибку, в трейсах.
- **Модель игнорирует новый путь.** Смягчается промпт-гейтом; проверяется по
  трейсам — вызовы `batch_design` с `U(…htmlContent…)` на существующем узле
  должны стать редкими.
